### 2.3 扫描规则（源码，决定"文件该放哪"）

- extra 配置的合并语义：`utils/extra_config.py:6-34` → 对每个 folder 调 `folder_paths.add_model_folder_path(x, path, is_default)`；`folder_paths.py:382-398` 对 `is_default=True` 是**插到列表最前**，**不删除**默认目录。所以本机 `unet` 的搜索列表是 `[共享\unet, 安装\models\unet]`（同理其它 folder）。
- 子目录递归：`folder_paths.py:404-443` `recursive_search` 会走子目录，返回相对路径；所以 `/object_info` 里出现 `MiniMax-H3\xxx.safetensors` 这种带反斜杠的项。
- 扩展名白名单：`folder_paths.py:10` `supported_pt_extensions = {'.ckpt','.pt','.pt2','.bin','.pth','.safetensors','.pkl','.sft'}`。不在这个集合里的文件名**不会**出现在列表里（`.part`、`.tmp`、`.download` 天然被排除，这正好可以用来做原子下载）。

## 4. 下载方案（按优先级；T14 照 §4.1 实现）

### 4.1 方案 a（**推荐**）：T14 自己按绝对路径下载，绕开 comfy-cli 的模型下载命令

设计原则：
1. **目录由 §4.4 的解析顺序得到**（不硬编码本机路径，不依赖 `comfyModelsDir`）；
2. 落盘名 = profile 在该 kind 上声明的 `folder`（`src/model-profiles.ts:521-607`）——与既有文件布局一致，也让插件报错里的「放到：…」与实际一致；
3. **临时名 `.part` 下载 → 校验字节数 → 原子改名**：`.part` 不在扩展名白名单，因此"半截文件"不会出现在 `/object_info` 里冒充成功；
4. **校验只认 `/object_info`**（§5），不以"文件存在"为成功。

### 4.2 方案 b（备选：如果必须用 comfy-cli 下载）

两条路线都**未实机核实**（本机未装 comfy-cli，安装属 T15），只给评估与验证方法：

- **b1：`--relative-path` 指到 Desktop 绝对路径**。README 只写了 `--relative-path <PATH>`，未说明是否接受绝对路径/是否强制相对 workspace（未核实）。若接受：`comfy model download --url <URL> --relative-path "D:\Comfy-Desktop\ComfyUI-Shared\models\unet"` 即可；若不接受：此路不通。
- **b2：把 comfy-cli workspace 指向 Desktop 安装目录**（`D:\Comfy-Desktop\ComfyUI-Installs\ComfyUI\ComfyUI`，即 `main.py` 所在目录）。comfy-cli 会写 `<workspace>\models\<relative-path>`，而**安装树的 `models\` 本来就在 ComfyUI 的默认扫描列表中**（`folder_paths.py:25-33` 的 `models_dir` 默认值；本机实测该目录下只有占位文件、被扫但为空）→ 落进去 `/object_info` **能看到**。
  - 代价：权重分散在两棵树（共享根 + 安装树），Desktop 的模型管理/迁移界面不认安装树里的文件；两套目录都要留空间；Desktop 更新时不要手动动安装树。
  - 结论：**技术上可行、工程上不推荐**；只有 b1 实测不通时才考虑。
- **b3：反向——改 Desktop 的 `modelsDirs` 指向 comfy-cli workspace**（Desktop 设置里就能改）。需要重启 Desktop、影响该安装下所有工作流，且不是 T14 的自动化面；仅适合用户手工场景，不进 T14 实现。

### 4.3 三种方案的关系（给协调者一句话）

> **T14 = 方案 a。** 方案 b 只在"用户已装 comfy-cli 且坚持用它"时作为人工兜底，且必须先跑 §3.3 的补测把"未核实"消掉；方案 c 不进自动化。

### 4.4 模型根解析顺序（T14 的实现规格）

按权威性从高到低，取第一个成功的；前一步失败才走下一步：

1. **运行中实例的 argv（最权威，代表"这个实例实际扫哪"）**
   `GET /system_stats` → `system.argv` → 找 `--extra-model-paths-config` 的下一个参数 → 读该 yaml 的 `base_path`（`utils/extra_config.py:14-19` 支持变量展开与相对修正；yaml 相对路径要按 yaml 所在目录解析）。
   - 若 argv 里有 `--base-directory`，按 ComfyUI 语义它是 `base_path`（默认 `models_dir` 的父）；与 yaml 的 `base_path` 二选一时**优先 yaml**（extra config 的 `is_default` 把共享根插到最前，这正是 Desktop 的意图）。
   - 若 argv 里**没有** `--extra-model-paths-config`（portable/源码版常见）：退回默认规则 `<ComfyUI 目录>\models`。
2. **实例没跑时**：`installations.json`（`status=installed` 且 `sourceId=standalone`）→ 取 `id` → `%APPDATA%\Comfy Desktop\instance-model-paths\<id>.yaml` → `base_path`。
3. **兜底**：`%APPDATA%\Comfy Desktop\settings.json` 的 `modelsDirs[0]`（注意：这是 Desktop 的"期望值"，可能与运行实例不一致，所以排第 2/3 位）。
4. **交叉校验**：拿 `/object_info` 里某个既有文件的相对名（如 `qwen_image_2.1_int8_convrot.safetensors`）反查，确认它确实落在解析出的 `base` 下；对不上就以 argv 那份为准。
5. **不要用**插件的 `comfyModelsDir` 做定位（§2.4 第三条）。

## 5. `/object_info` 校验判据（**唯一判据**）

### 5.1 判据定义

**下载成功 = 用同一个 endpoint 请求 `GET /object_info/<该权重对应的 Loader>`，在其返回 JSON 里
`<Loader>.input.required.<field>[0]`（字段可能在 `input.optional`）**是一个字符串数组，且数组 **包含期望的精确文件名**。

本机四个 Loader 的实测返回形状（截取）：

```json
// GET /object_info/UNETLoader
{"UNETLoader":{"input":{"required":{"unet_name":[["qwen_image_2.1_int8_convrot.safetensors", …]],"weight_dtype":[…]}}}}

// GET /object_info/CLIPLoader
{"CLIPLoader":{"input":{"required":{"clip_name":[["qwen3vl_8b_int8_convrot.safetensors", …]],"type":[…]}}}}

// GET /object_info/VAELoader
{"VAELoader":{"input":{"required":{"vae_name":[["qwen_image_2.1_vae_bf16.safetensors", …]]}}}}
```

与插件现有实现同构（`src/comfyui.ts:510-517` `loaderField`：先 `input.required[field]`、退化到 `input.optional[field]`，取 `[0]` 数组）；插件在提交 `/prompt` 之前就是用这份列表选权重（`src/comfyui.ts:599-636`），所以**它看到什么，就是 ComfyUI 加载时会用什么**。

### 5.2 判据的三条纪律

1. **精确文件名匹配，不用正则**：插件自己的选权重是"required + bonus 打分"（`src/comfyui.ts:535-545`）。用正则做下载校验会误判——例如 Qwen 文本编码器 required 只是 `/qwen/i`，只下了 PE 增强编码器（`qwen3.5_9b_qwen_image_2.1_pe_i2i…`）也会"匹配"，但不是 MOSS/Qwen 要的那个。**下载器的判据必须是"期望文件名 ∈ 数组"**。
2. **子目录文件用反斜杠形式**：`MiniMax-H3\minimax_h3_ref2va_pruned_int8_convrot.safetensors`。T14 下载到根目录时就是纯文件名；放到子目录时要按 ComfyUI 返回的写法比对（Windows 上是 `\`）。
3. **"能看到" ≠ "文件完整"**：`/object_info` 只做目录列举，不读文件内容、不校验大小。所以顺序必须是「`.part` 下完 → 大小校验 → 改名 → 再探 `/object_info`」，否则会出现"探测成功但加载报 `Error while deserializing header`"（`docs/comfyui-deployment.md:293-301` 已记录这类排障）。

### 5.3 刷新语义（要不要重启 ComfyUI？）

- 源码事实：`folder_paths.py:493-527` 的文件列表缓存按**目录 mtime** 失效（`cached_filename_list_` 逐个 `os.path.getmtime` 对比；目录 mtime 变了就重扫）；`server.py:892-903` 的 `/object_info` 处理期间用 `with folder_paths.cache_helper:` 只做单请求内强缓存。
- **推论：新增/改名一个文件（目录 mtime 变化）后，下一次 `/object_info` 应当自动看到，不需要重启。** 这也解释了为什么"下载到一半"的文件（扩展名合法的话）会被提前列出——所以临时扩展名很重要。
- **未核实项**：本任务只读、没有往模型目录写过文件，上述是源码结论不是实测结论。**T14 首单必须做一次实测**：下载 → 不重启 → 立刻探 `/object_info` → 记录结果（成功则回填本文；若真遇到缓存，兜底是重启 Desktop 的 ComfyUI 实例，并记录触发条件）。

## 6. 失败模式：「下完了但探测说没有」的排查顺序

> 顺序是刻意的：先排除**我们自己的落盘错**，再怀疑缓存，最后才怀疑进程链。四层进程链是最后一层，因为它最贵且最少见。

**Step 0 — 确认你问的是同一个 ComfyUI**
- `curl -s <endpoint>/system_stats` 能通吗？`system.argv` 的端口和 `comfyPorts`/`comfyEndpoint` 是同一个实例吗（本机 8188，历史上出现过 8189/8190 的日志文件）？多实例/旧进程占端口时，探测与出图可能指向不同进程。

**Step 1 — 目录（最常见）**
- 拿 §4.4 解析出的 `base` 与"文件实际落盘的绝对路径"**逐字符比对**：是不是落到了 `<HOME>\comfy\ComfyUI\models`（comfy-cli 默认）、`<ComfyUI 安装目录>\models`（本机是空树）、还是别的地方？
- 目录名是否落在 yaml 映射的键里（`unet`/`diffusion_models`/`clip`/`text_encoders`/`vae`/`loras`）。**放进 yaml 没映射的自造目录 → 永远看不到**。
- Desktop 改过「模型路径」后：重新读 `instance-model-paths\<id>.yaml`（会重新生成），别用旧值。

**Step 2 — 文件名 / 扩展名**
- 是否还叫 `*.part` / `*.tmp` / `*.download`（不在白名单，必然看不到）——这是**原子下载没做完**的典型症状。
- 扩展名是否在 `folder_paths.py:10` 白名单内；大小写不敏感但**中文/空格/括号文件名**能列出、却可能过不了插件的打分正则（进入 Step 4）。
- 是否落在子目录里（返回名会带 `子目录\` 前缀），比对方式是否一致。

**Step 3 — 扫描 / 缓存**
- 再请求一次 `/object_info/<Loader>`（换个 endpoint/加时间戳无用，缓存是进程内的，按 mtime 失效）；仍未出现 → 确认不是刚在"同一 mtime 秒"内改的目录（Windows 目录 mtime 精度足够，但极端情况下重试一次即可）。
- 兜底：重启该 ComfyUI 实例（Desktop 界面右上角重启 / 停进程再起）。能刷新说明是缓存，不能刷新说明目录/文件名错（回 Step 1/2）。

**Step 4 — 文件名打分（`/object_info` 明明有，插件仍报"缺模型"）**
- 插件的报错会**把"当前能看到 N 个"列出来**（`src/comfyui.ts:624-632`），直接拿它和 profile 的匹配规则对照：
  - Qwen DiT：`required /qwen/i`，bonus `/image/i, /2[._-]?1/, /int8/i`，base 额外 `avoid /turbo/i`，turbo 反过来 `bonus /turbo/i`（`src/model-profiles.ts:522-563`）。
  - Qwen 文本编码器：`required /qwen/i` + bonus `/vl/i, /8b/i, /int8/i`——**PE 编码器（pe_t2i/pe_i2i）没有 `vl`/`8b`**，若目录里只有 PE 会被选中但大概率加载错（这也是 §5.2 要求精确名判据的原因）。
  - Qwen VAE：`required /qwen/i` + `vae/2.1/bf16`。
  - MOSS DiT：`required /moss/i` + `sft/image/int8`；MOSS VAE：`required /flux[._-]?2/i` + `vae/small`；**MOSS 文本编码器最严**：`required /qwen3[._]?5.*(?:w4a8|gptq)/i`——文件名里必须带 `w4a8` 或 `gptq`，否则选不出来（`src/model-profiles.ts:575-607`）。
- 交叉验证工具：`node scripts/start-comfyui.mjs --doctor`（按角色列 5 个权重，`scripts/start-comfyui.mjs:293-321`；它的正则与插件不同口径，只作旁证）。

**Step 5 — 最后才怀疑"四层进程链"**
- 链路（T15 之后）：**插件工具面 → comfy-mcp → comfy-cli(comfy) → ComfyUI**。判据：**同一 endpoint 用 curl 直连 `/object_info` 能看到新权重，但插件/MCP 侧报"读不到/缺模型"** → 目录没问题，问题在链上游（MCP spawn 的环境变量/参数、`comfy-mcp` 的 discover、`comfy-cli` 的 workspace 指向别处）。
- 本阶段（P0 基线）**还没有 MCP 层**：插件是直接用 HTTP 打 `/object_info`（`src/comfyui.ts:604-608`）。所以现在的"链"只有两层：插件进程 → ComfyUI；排查时先确认两者 endpoint 一致，再谈四层。
- 排障取值点：`/system_stats.argv`（是不是同一个进程）、`comfy which`（T15 后）、MCP spawn 日志、进程树。
